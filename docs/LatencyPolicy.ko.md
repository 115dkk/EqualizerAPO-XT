# 지연 억제 정책

[English](LatencyPolicy.md)

Equalizer APO XT는 사용자가 요청하지 않은 지연을 소리에 붙이지 않습니다.
64비트 처리와 마찬가지로 이 프로젝트의 정체성에 속하는 원칙입니다. 기본 신호
처리에 지연이 생기는 변경은 버그이고, 버그로 다룹니다.

이 문서에는 그 원칙이 지금 코드에서 어떻게 지켜지는지, 어느 부분을 업스트림
Equalizer APO에서 물려받았고 어느 부분을 여기서 설계했는지, 사용자가 지연을
고를 수 있는 곳이 어디인지, 기여자가 무엇을 지켜야 하는지를 작성했습니다.

## 여기서 말하는 지연

지연이라고 부르는 것은 세 가지이고, 정책은 셋을 다르게 다룹니다.

- **엔진이 붙이는 지연.** 샘플이 엔진에 들어와서 나갈 때까지 엔진의 동작
  방식 때문에 생기는 고정된 샘플 수입니다. 버퍼에 쌓아 두기, 블록 크기 다시
  묶기, 블록을 다른 스레드에 넘기고 나중에 받기가 원인입니다. **정책의
  대상은 이 지연이고, 기본값은 0입니다.**
- **필터 자체의 지연.** 선형 위상 임펄스 응답은 자기 길이의 절반만큼
  늦습니다. 최소 위상 이퀄라이저, 올패스, IIR 밴드에는 주파수에 따라 달라지는
  군지연이 있습니다. 사용자가 고른 필터의 성질이고, 올바르게 구현한
  프로그램이면 어디서나 같습니다. 엔진은 여기에 더하지도 않고 감추지도
  않습니다.
- **엔진 밖의 지연.** 장치의 버퍼, 드라이버, Windows 오디오 엔진, 그리고
  신호가 거치는 다른 프로그램입니다. 엔진이 바꿀 수 없는 부분입니다. 다만
  프로그램과 버퍼를 하나 더 거치지 않게 할 수는 있습니다. VST 호스트,
  컨볼버, 라우팅이 모두 한 번의 처리 호출 안에서 도는 이유입니다.

## 기본 상태의 처리

설치 기본값에서 APO는 Windows에서 블록을 받아 같은 콜백 안에서 제자리로
처리하고 돌려줍니다. 입력과 출력 사이에 대기열이 없으므로, 샘플은 들어온
블록에 담겨 나갑니다.

| 부분 | 붙는 지연 | 방법 |
|---|---|---|
| APO의 블록 처리 | 0 | 블록이 들어온 콜백 안에서 처리합니다(`EqualizerAPO/ApoFormat.h`). |
| 설정 변경 | 0 | 10ms 동안 옛 설정과 새 설정이 같은 블록을 함께 처리하고 둘을 교차 페이드합니다(`engine/FilterEngine.cpp`). |
| 컨볼루션(길이 무관) | 0 | 파티션 크기가 장치의 블록 크기입니다. 긴 응답은 2단 컨볼버가 처리하는데, 꼬리 계산이 아직 끝나지 않은 구간을 머리가 맡습니다(`libHybridConv-0.1.1/libHybridConv_eapo.cpp`). |
| 다중 코어 컨볼루션 | 0 | 워커와 오디오 스레드가 호출이 끝나기 전에 그 블록을 함께 마칩니다(`runtime/concurrency/RealtimeFanOut.cpp`). |
| GraphicEQ | 0 | 최소 위상 응답을 같은 컨볼버로 처리합니다. |
| IIR 필터, 프리앰프, 복사, 라우드니스 | 0 | 샘플 단위로 처리합니다. |

우선순위는 다음 세 경우에서 드러납니다. 셋 다 버퍼링으로 해결할 수 있었지만
다른 방법을 택했습니다.

- **예상과 다른 크기의 블록.** 컨볼버는 장치의 블록 크기에 맞춰 만듭니다.
  다른 크기의 블록이 오면 그 블록의 컨볼루션 출력을 음소거하고, 횟수를 세어
  나중에 보고합니다. 블록을 다시 묶으면 샘플을 붙잡아 두어야 하므로 다시
  묶지 않습니다.
- **알려 준 최대 크기보다 큰 블록.** 잘라서 대기열에 넣지 않고 처리 없이
  그대로 통과시킵니다.
- **긴 임펄스 응답.** 파티션을 크게 잡으면 계산은 싸지지만 한 블록의 지연이
  생깁니다. 2단 컨볼버는 응답의 앞부분에 작은 파티션을 그대로 쓰고, 나머지
  계산을 뒤따르는 콜백들에 나눠 처리합니다.

## 물려받은 것과 여기서 설계한 것

**업스트림 Equalizer APO 1.4.2에서 물려받은 것:**

- APO 콜백 안의 제자리 처리.
- 설정 사이의 10ms 교차 페이드.
- 장치의 블록 크기를 파티션으로 쓰는 컨볼루션.
- `Delay:` 명령과 최소 위상 GraphicEQ.
- '무음 버퍼 수정 허용' 옵션. 입력이 무음이 된 뒤에도 늦춘 소리와 꼬리가
  끝까지 재생되게 합니다.

**이 포크에서 설계한 것(지연을 붙이지 않는 것이 요구 사항이었습니다):**

- 긴 응답을 위한 2단 컨볼버(#483).
- 같은 블록 안에서 일을 나눠 마치는 다중 코어 컨볼루션과, 측정한 블록 처리
  시간으로 워커 수를 정하는 관리자(#514).
- 블록 크기가 다를 때 다시 초기화하거나 다시 묶지 않고 음소거하는 처리와,
  너무 큰 블록의 통과.
- 상태나 꼬리를 가진 필터가 없을 때에만 무음 입력의 처리를 건너뛰는 동작.
- VST 지연 보정. 플러그인의 상태를 불러온 뒤 지연을 다시 읽고, 플러그인이
  쓰지 않는 채널만 같은 만큼 늦춰 모든 채널이 필터에서 나란히 나갑니다.
- ASIO 래퍼의 동기 모드. 버퍼 전환 안에서 기다리며 버퍼를 추가하지 않습니다.

## 사용자가 고르는 지연

아래 항목은 모두 설정 파일에 적혀 있거나, 무엇을 얻고 잃는지 옆에 적힌
옵션으로 정합니다.

| 선택 | 지연 | 정하는 곳 |
|---|---|---|
| `Delay: <t> ms` 또는 `<n> samples` | 고른 채널에 정확히 그만큼. | 설정 파일 |
| 지연을 보고하는 VST 플러그인 | 플러그인이 보고한 만큼, 필터에서 나가는 모든 채널에. | 설정 파일 |
| `Hilbert:` | 옮기는 채널과 `Align=`에 적은 채널에 512샘플. | 설정 파일 |
| `Send:`의 `Latency=` | 보내는 장치와 받는 장치 사이의 D. 기본값은 보내는 쪽 처리 주기의 두 배입니다. `Compensate=`(기본 켜짐)는 보내는 장치 자신의 채널도 D만큼 늦춰 두 장치를 맞춥니다. | 설정 파일, Send 카드 |
| '전송된 오디오 리샘플링' | D 밖에서 더 생기는 지연은 없습니다. 리샘플러의 48프레임 지연은 D 안에 포함됩니다. 요청할 수 있는 가장 작은 D가 그만큼 커집니다. | Device Selector |
| 선형 위상 임펄스 응답 | 길이의 절반. 응답의 성질입니다. | 사용자가 불러온 파일 |
| ASIO 래퍼의 버퍼(기본) 또는 '버퍼 제거' | 버퍼가 있으면 ASIO 버퍼 하나가 더해지고 그 값을 프로그램에 보고합니다. 제거하면 더해지지 않고, 제때 준비되지 않은 블록은 처리 없이 재생됩니다. | Device Selector |

기본값이 지연을 붙이는 곳은 ASIO 래퍼 하나입니다. 버퍼 하나이고, 64프레임과
48kHz에서 1.3ms입니다. 래퍼는 블록마다 별도의 엔진 프로세스에 넘기는데, 실제
하드웨어에서는 운영체제가 두 스레드 중 하나를 버퍼 하나보다 오래 멈춰 세울
때가 있습니다. 버퍼가 없으면 그 블록은 이퀄라이저를 거치지 않은 소리로
나갑니다. 그래서 버퍼를 둔 쪽을 기본값으로 정했습니다. 이 버퍼는 프로그램에
보고되므로 녹음의 정렬은 유지되고, 체크박스 하나로 없앨 수 있습니다. 대부분의
사용자가 쓰는 APO에는 프로세스 사이로 넘기는 과정이 없고 이런 버퍼도
없습니다.

## 숫자로 확인하기

- `FilterEngine::getRealLatency()`는 불러온 설정이 붙이는 고정 지연을
  돌려줍니다. 출력 채널 중 가장 큰 값이고, 채널별 값은
  `getRealLatencyByChannel()`로 얻습니다. Benchmark가 이 값을
  출력합니다(`Real latency: <n> samples`). 위 표에서 샘플 수가 정해진 항목만
  셉니다.
- APO의 `GetLatency`에는 이 값이 들어가지 않습니다. 업스트림과 같이 0을
  보고하고, 제조사 APO가 붙어 있으면 그 APO의 지연을 더합니다. Windows에
  알리는 값이 달라지면 Windows가 스트림을 다루는 방식이 달라질 수 있어 그대로
  두었습니다.
- ASIO 래퍼는 자기 버퍼 하나를 프로그램에 보고하는 지연에 더합니다.
- Editor의 분석 패널은 측정 전에 뺀 지연을 표시하고, '기본 지연 포함'을 켜면
  위상과 군지연 곡선에 그 지연을 다시 넣습니다.
- 설치된 APO를 루프백으로 재서 이 값과 대조했습니다. 컨볼루션이 26개까지
  들어가는 세 장면에서 APO가 더 붙인 지연은 0샘플이었습니다. 측정 방법과, 같은
  장면을 CamillaDSP와 옴니포니로 돌린 결과는
  [지연 벤치마크](LatencyBenchmark.ko.md)에 있습니다.

## 아직 하지 않은 것

- 고정 지연이 서로 다른 두 설정을 교차 페이드할 때 둘을 맞추지 않고
  섞습니다. 10ms 동안 두 설정의 소리가 서로 다른 시점에 나옵니다.
- 받는 장치의 주기를 따라가는 `Send:`의 `Latency=Auto`는 구현되지
  않았습니다.

## 지킬 것

이 저장소에 변경을 올릴 때 아래 여덟 가지를 지키십시오.

1. **기본 상태에서는 지연을 붙이지 마십시오.** 기본 신호 처리에 대기열, 두
   번째 블록 크기, 블록 경계를 넘는 전달을 넣는 변경은 CPU를 얼마나 아끼든
   받지 않습니다.
2. **일은 블록 안에서 나누고, 블록 사이로 미루지 마십시오.** 스레드를 늘리는
   것, 계산을 싸게 만드는 것, 머리가 이미 맡은 구간 뒤로 계산을 미루는 것은
   모두 괜찮습니다. 블록을 늦게 돌려주는 것은 안 됩니다.
3. **지연과 정직한 실패 중에서 골라야 하면 실패를 고르십시오.** 음소거하거나,
   그대로 통과시키거나, 처리하지 않은 블록을 재생하고, 횟수를 세어 오디오
   스레드 밖에서 보고하십시오. 문제를 가리려고 몰래 버퍼링하지 마십시오.
4. **지연은 사용자가 고르게 하고, 값은 정확하게 하십시오.** 지연이 필요한
   기능에는 옵션이나 설정 매개변수를 두고, 가능하면 기본값을 지연 없음으로
   하며, 조작부 옆에 대가를 적으십시오. 예외를 두려면 ASIO 버퍼처럼 측정에
   근거한 이유를 적어 두십시오.
5. **채널을 맞추십시오.** 일부 채널을 늦추는 필터에는 나머지 채널을 같은
   만큼 늦출 수단을 함께 넣으십시오(VST 보정, `Align=`, `Compensate=`).
6. **보고하십시오.** 고정 지연을 붙이는 필터는 `IFilter::reportLatency`를
   재정의해 실제 지연 값이 사실과 맞게 하십시오.
7. **테스트하십시오.** 신호 처리를 새로 만들거나 바꾸면 레벨뿐 아니라 샘플
   위치를 비교하는 테스트도 넣으십시오. 본보기는 기존 테스트입니다. 2단
   컨볼버를 직접 컨볼루션과 비교하는 테스트, 지연 512인 플러그인으로 VST
   보정을 확인하는 테스트, Send의 D가 정확한지 보는 테스트, 동기 모드가
   지연을 더하지 않는지 보는 테스트가 있습니다.
8. **재지 않은 것을 주장하지 마십시오.** 문서에 적는 숫자는 테스트, 방법을
   밝힌 측정, 코드 중 하나에서 가져오십시오.
