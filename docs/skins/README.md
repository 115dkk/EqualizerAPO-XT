# 스킨 헌법 (Skin constitutions)

Editor의 5개 스킨이 각자 무엇을 믿고, 무엇을 금지하며, 새 UI 요소가 생길 때
어떻게 답해야 하는지를 기록한 문서 묶음이다. 절차와 규율(훅 계약, 갤러리,
중립 기본값 증명)은 [skin-hooks.md](../skin-hooks.md)와
[skin-integration-report.md](../skin-integration-report.md)에 있고, 이 디렉터리는
**디자인 철학 그 자체**를 보존한다. 스킨 프로그램(#66→#67→#68, v1.18~v1.19)과
픽커 라운드(#81, v1.22)를 거치며 격리 에이전트들과 통합 심사가 축적한 뉘앙스를
사람이 다시 읽을 수 있는 형태로 적어 둔 것이다.

| id | 이름 | 한 줄 정체성 | 헌법 문서 |
|---|---|---|---|
| `studio` | Studio Glass | 빛이 비치는 유리 뒤의 악기. UI는 데이터 뒤로 물러난다 | [studio.md](studio.md) |
| `minimal` | Precision Minimal | 은행 창구의 단말기. 활자·헤어라인·정렬이 전부다 | [minimal.md](minimal.md) |
| `soft` | Soft Lab | 두려울 수 없는 설정 화면. 둥글고 넉넉하다 | [soft.md](soft.md) |
| `rack` | Hardware Rack | 19인치 랙의 앰프 페이스플레이트. 손에 닿을 듯한 기계 | [rack.md](rack.md) |
| `matrix` | Signal Matrix | 공항 출발 안내판 / 방송 라우팅 매트릭스. 좌표를 가진 셀의 보드 | [matrix.md](matrix.md) |

## 다섯 스킨이 함께 지키는 것

각 헌법은 아래 공통 기반 위에서만 갈라진다.

- **차별화 게이트.** 어떤 항목에서든 두 스킨이 "팔레트만 다르면" 실패다. 새 UI
  요소(행 chrome, 노브, Copy 표현, 픽커 등)가 생기면 다섯 스킨이 각자의
  철학으로 **따로** 답해야 하며, 통합 시 7개 항목(타입 표시, 호버, 비활성,
  Include 행, VST 행, 모서리/엣지 언어, 위계의 주도자)으로 심사한다. 기준과
  판정 기록은 skin-integration-report.md에 있다.
- **토큰만 사용.** 색은 `SkinTokens`(코드)와 `@TOKEN@` 치환(QSS)으로만 쓴다.
  테마(다크/라이트)별 하드코딩은 금지다. 훅은 모드 플래그를 받지 않으므로,
  모드 분기가 꼭 필요하면 배경 명도로 추정한다(공유 `skinIsDark` 헬퍼, SkinPaint.h).
- **중립 기본값 규칙.** `ISkin`에 훅을 추가할 때 기본 구현은 기존 모습과 픽셀
  단위로 동일해야 하고, 갤러리 PNG SHA-256 비교로 **증명**한다(가정하지 않는다).
- **행 재생성.** 스킨별 chrome·렌더러·픽커는 위젯 생성 시점에 만들어진다. 스킨
  전환은 `FilterTable::updateGuis()`의 행 재생성으로 반영된다. 재칠(update)만으로
  바뀌리라 기대하지 말 것.
- **갤러리가 증거다.** `Editor --skin-gallery <outDir>`가 스킨×다크/라이트로
  대표 행 6종×상태 3종 + 필터 픽커 3장 + chrome 4장 = 총 250장을 렌더링한다.
  행 안에 가로 스크롤바가 보이면 렌더가 실패한다(960px 뷰포트 준수 게이트).
  외형 변경은 갤러리로 확인하고, 무간섭 주장은 바이트 비교로 증명한다.
- **상호작용 계층은 공유한다.** 입력 처리(AudioKnob의 드래그/휠/키보드,
  픽커 호스트의 팝업/이벤트 루프, Copy의 파싱/직렬화)는 스킨이 소유하지
  않는다. 스킨은 표현만 바꾼다.

## 헤더 컨트롤 열의 공유 계약 (2026-08-23 사용자 결정)

카드 헤더의 컨트롤(전원, `+`, `-`, 원문 편집)은 번호 바로 뒤의 **고정 왼쪽
열**에 선다. 순서는 `[펼침][번호][전원][+][-][편집][종류 배지][제목][요약]
[채널 배지][여백]`이며, 요약은 제 글자 폭만 차지하고 남는 폭은 끝의 여백이
가진다. 원본 Equalizer APO의 행(번호, 툴바, 전원 스위치가 왼쪽, 내용이 그
뒤)과 같은 배치다. 27인치 화면의 제보("내용은 왼쪽에 있는데 버튼은 오른쪽에
있어 눈을 많이 굴린다")로 굳어졌다. 스킨은 이 순서를 바꾸지 않는다. 스킨이
헤더 오른쪽 끝에 그리던 판독값(minimal의 워치 칼럼, matrix의 판독 셀,
studio의 `= 값`)은 버튼 열을 피하려던 예약 폭을 버리고 오른쪽 가장자리까지
쓴다.

## 카드 추가·삽입의 공유 계약 (2026-07-26 사용자 결정)

상호작용 계층은 스킨이 소유하지 않으므로, 카드 추가의 의미론은 다섯 스킨이
공유한다. 스킨은 표현만 답한다.

- **헤더 `+`는 위(앞) 삽입이다.** 카드 헤더의 `+`는 그 카드 *바로 앞* 위치에
  새 카드를 만든다. 사용자가 현재 카드에 도달하기 직전에 처리할 필터를
  붙인다는 문법이며, 모든 스킨이 같은 위치 의미론을 공유한다.
- **맨 앞 호버 삽입선도 유지한다.** 리스트 최상단(첫 카드 위) 경계에서만
  마우스 호버 시 삽입선이 나타나, 클릭하면 맨 앞 위치에 삽입한다. 첫 카드의
  헤더 `+`와 결과는 같지만, 긴 카드의 헤더 버튼을 찾지 않아도 되는 직접
  진입점이다. 평상시에는 그리지 않는다(상시 노출 금지).
- **카드 사이마다 상시 `+`를 늘어놓지 않는다.** (사용자 판정: "매 카드 사이
  +는 이쁘지 않다") 카드 간 삽입은 다음 카드의 헤더 `+`(위 삽입)와 드래그가
  담당한다.
- **맨 끝 add row는 상시 노출이다.** 목록 마지막의 '카드 추가' 행은 항상
  보인다. 이 행은 레거시 툴바가 아니라 스킨별 프레젠테이션을 입어야 하며,
  호버 삽입선의 표현과 함께 각 헌법 문서가 답한다.

## 공유 조문 — 라운드가 세운 법

아래 조문은 특정 스킨의 표현이 아니라 다섯 스킨이 함께 지키는 규범이다.
개별 캠페인의 심사에서 나왔지만, 판정의 이유가 스킨 고유의 철학이 아니라
정보 전달의 문법이었기에 총강으로 승격했다. 각 헌법 문서는 이 조문을
되풀이하지 않고 자기 스킨의 형태만 답한다.

1. **상태는 한 번 말한다.** 판정을 램프(그 스킨의 상태 표기)가 들고 있으면
   그 옆에 같은 뜻의 단어를 붙이지 않는다. 값은 컨트롤이, 문장은 카드
   상태 줄이 이미 소유하므로, 램프 곁의 단어는 램프를 두 번 말하는
   사족이다. (판례: VST 버스 r2, 'Rejected' 각인 제거)
2. **정체성 사실은 기존 장식이 게시한다.** 로드된 ABI(VST2/VST3) 같은
   사실은 스킨이 이미 세워 둔 장식(rack의 황동 명판, matrix의 포트 스트립
   각인)이 게시한다. 같은 사실을 본문의 별도 배지·스탬프·코드 셀로
   되풀이하면 눈에 거슬리는 재탕이 된다. (판례: VST 버스 r3)
3. **문제는 스킨의 상태 문법이 먼저 말한다.** 긴 설명문 단독으로 문제를
   알리지 않는다. 각 스킨이 이미 가르친 상태 표기(soft 타일의 스트로크
   느낌표, rack의 베젤 LED, matrix의 비컨, minimal의 잉크 태그)가 먼저
   말하고, 문장은 사실과 결과만 담아 짧게 잇는다. (판례: VST 버스 r3)
4. **폭 압박의 우선순위.** 960px에서 행이 넘치면 데이터 열(위치, 이름)이
   엘리전으로 먼저 물러나고, 명령어·액션의 각인은 마지막까지 온전하다.
   잘린 명령어는 아무것도 전달하지 못하지만, 줄어든 데이터는 툴팁이
   받친다. (판례: VST 버스 r1, minimal 커맨드 눌림)
5. **방향·캐럿 글리프는 페인트로 그린다.** 폰트 커버리지가 화살표의
   존재를 결정하게 두지 않는다(DM Mono의 두부 함정). 텍스트로 쓰는
   화살은 ASCII만 허용한다. (판례: AR2 재작업, VST 버스 r1)
6. **컨트롤은 그 스킨이 가르친 '누를 수 있는 형태'를 입는다.** 맨 외곽선
   이나 투명 캡션 단독은 버튼으로 읽히지 않는다. 그 스킨의 격자·필·캡이
   이미 가르친 휴지 형태를 재사용해야 학습 비용 없이 컨트롤로 읽힌다.
   (판례: 게이트 #176, VST 버스 r2)

## 헌법 문서의 사용법

새 위젯이나 화면을 추가할 때는 해당 스킨의 헌법 문서를 먼저 읽고, 그 문서의
**"새 요소를 이 스킨답게 만드는 법"** 체크리스트에 답하는 방식으로 설계한다.
다섯 스킨을 동시에 작업할 때는 스킨 프로그램의 패턴(스킨당 격리 에이전트 1개,
허용 파일 집합 고정, 갤러리 자기 검증, 통합자 차별화 심사)을 재사용한다.

문서가 코드와 어긋나면 코드가 아니라 문서를 의심하라. 단, "하지 말 것" 절은
코드보다 오래 산다. 그 절은 실수 사례나 기각된 설계에서 나온 것이므로, 코드에
위반 사례가 없다는 이유로 지우지 않는다.
